##### ＜採用理由＞

###### フレームワーク噛み合っていた



自分のフレームワークでは、

・3Dステルス（TPS）ゲーム前提（プレイヤー・敵・弾・地形など、多数オブジェクト）

・将来的にステージ数や敵数が増えても耐えられるパフォーマンス

・キャラクター用の挙動（床に沿って移動、段差・坂の処理など）が重要

・C++で自身のフレームワークに統合しやすい API が欲しかった



Jolt は

・3D用

・マルチスレッド前提の設計で高速

・キャラクター向けの機能（CharacterVirtual）が最初から用意されている

・C++17 ベースで、自作のエンジンコードに組み込みやすい

という点が噛み合った。



###### オープンソースでライセンス的に扱いやすい

今後、個人制作やポートフォリオで使い続けることを考えたとき、ライセンス面で余計な制約が少ない方がよい。

・ソースが読めるので、「なぜこう動くのか」をある程度は自分で追える。

・フレームワーク自体も長期的に育てていく前提なので、中身がある程度見えるライブラリを選びたかった、という理由もある。



3\. 設計がシンプルで、自前フレームワークと相性が良い



自分のフレームワークでは、

物理マネージャーを中心にRigidbodyやColliderなどのコンポーネントを生やす

→ゲームオブジェクトと物理オブジェクトを 1 対 1 で結びつける、という構造になっている。



Jolt も

・PhysicsSystem がメインの窓口

・BodyやBodyInterface周りがシンプル

・レイヤ分け（Static / Dynamic）や、フィルタ用のコールバックなどが素直な設計



になっていて、自分の「GameObject + Component」の構造に綺麗にマッピングしやすかった。

たとえば、

・BoxCollider → JPH::BoxShape

・Rigidbody → JPH::Body（Dynamic / Static の切り替え）

とか...。

という対応が取りやすく、ラッパークラスの実装コストがそこまで高くならないと判断した。



###### キャラクター向けの機能が充実している

今回のゲームはTPSで、プレイヤー・敵ともに「人型キャラクター」が前提。

・段差を登る

・坂を下る／上る

・障害物を乗り越えないようにする

・床の法線を見て、足場に沿って動く

といったキャラクターならではの処理は、一般的な Rigidbody だけで実装しようとするとかなり大変。



Jolt には

・物理挙動ではなく「キャラ移動用」に特化した CharacterVirtual が用意されている

・カプセルによるキャラクターの当たり判定、ステップ処理などが一通り揃っている

といった利点があり、**「キャラクターの移動部分を早めに形にしたい」**という今回の開発方針と合っていた。



###### パフォーマンスと拡張性

今後、

・敵の数が増える

・弾やギミックなど、同時に動く物理オブジェクトが増える

・将来的に広いマップや多層構造のステージを試したい

といった拡張を考えると、物理エンジンの性能を最初から意識しておく必要がある。



Jolt は

・マルチスレッド対応を前提とした設計

・ブロードフェーズ／ナローフェーズともに高速

・実際の商用タイトルでも使われており、ある程度実績がある（推測です）

という背景から、「長期的に見ても潰しが効く選択肢」と判断した。



###### その他ライブラリとの比較

PhysX / Havok

→ 高機能だが、個人がソースを追ったり、軽く改造したりするには重い。自作フレームワークとの距離感も含めて、今回は見送った。（推測です）



Bullet

→ 実績は十分あるが、キャラクターまわりを Jolt の CharacterVirtual ほどスムーズに扱えるイメージが持てなかった。自分の中で「今から新しく覚えるなら Jolt に寄せる」と割り切った。



・◎C++17ベースで読みやすい

・キャラクター制御機能が最初からある

・API がシンプルで、ラッパーを自作しやすい

・将来のパフォーマンス要求にも対応しやすい
